# 联络函：请为 tenderforge 登记并授权六个 Atlas endpoint

- Stamp: 2609111009（2026-09-11 10:09）
- From: tenderforge 线
- To: Atlas 线（抄送平台线）
- Status: open（阻塞产品的全部 AI 能力）

## 一句话

产品侧已按 Atlas 契约接入完毕，**缺的是这六个 endpoint 在 Atlas 侧的登记、配置与
授权**。在 `product_endpoint_grants` 到位之前，每一次调用都是 `403 NOT_ENTITLED`，
与令牌是否有效无关。

## 为什么是「配置请求」而不是请求参数

`POST /v1/chat` 的请求体只有 `{endpointCode, messages, tenantId, taskId, requestId}`
——没有 `temperature`、没有 `max_tokens`、没有 thinking 开关。这不是遗漏：
`endpointCode` 的定义就是「运营侧配置好的具名路由目标」，生成参数属于那个配置。

所以下表里的参数不是我们想在请求里带的东西，而是**这个 endpoint 必须被配成什么**。
这些数字原本是本产品直连模型时自己发的参数，逐条实测调出来的；迁到 Atlas 之后
必须在 endpoint 配置里复现，否则同一份提示词会产出不同质量的结果——
**而这件事没有任何错误码**，只会让标书变差。

最典型的一对：`chapter_drafting`（温度 0.4、不开 thinking）与 `consistency_review`
（温度 0.0、开 thinking）。并到一个 endpoint 上，要么审查失去推理深度，要么正文
变得刻板重复。两种都只在读标书的时候才看得出来。

## 六个 endpoint

| endpointCode | 档 | temp | max_tokens | thinking | 上下文下限 |
| --- | --- | --- | --- | --- | --- |
| `chat/tenderforge-fast-deterministic` | fast | 0.0 | 8192 | 关 | 64K |
| `chat/tenderforge-quality-planning` | quality | 0.15 | **16384** | 关 | 64K |
| `chat/tenderforge-fast-planning` | fast | 0.2 | 8192 | 关 | 32K |
| `chat/tenderforge-fast-drafting` | fast | **0.4** | 提供方默认 | 关 | 32K |
| `chat/tenderforge-quality-revision` | quality | 0.2 | 提供方默认 | 关 | 32K |
| `chat/tenderforge-quality-review` | quality | 0.0 | 提供方默认 | **开** | **128K，500 页标书需 256K** |

### 各自的用途与理由

**`fast-deterministic`** —— 解读阶段三件事实搬运：从整份招标文件挑证据片段、
抽项目概述、技术评分条款排序（3 个 operation）。三件都不允许发挥：挑片段只返回
id 列表，任何随机性都是噪声；评分条款一旦被改写分值、档位或证明材料要求，
标书直接作废——这是整条链上唯一「错一个字就全废」的环节。

**`quality-planning`** —— 目录的一二级骨架。骨架决定整份标书的结构，一次定生死：
它错了，后面所有正文都写在错的框架里。`max_tokens` 的 16384 是**实测下限**，
更小会截断。

**`fast-planning`** —— 三级目录分批展开。量最大的规划环节，一份 500 页标书有
十几批。骨架已定结构，展开是填充，放 quality 上成本翻几倍而质量提升有限。

**`fast-drafting`** —— 正文续写。**调用次数占全流程绝大多数**，每个写作单元一次，
这一档的单价直接决定一份标书的成本。温度 0.4 是正文需要的表达变化：温度低了，
一份 300 页标书读起来像同一段话重复了三百页。`max_tokens` 刻意留空——正文该多长
由目录页数预算决定，不该被产品这一侧钉死。

**`quality-revision`** —— 章节局部 AI 修订，以及自动修订轮次里的定点修改。
受约束改写要贴合上下文所以走 quality；**刻意不开 thinking**——补全预算要留给
替换正文本身，花在推理上等于让改写结果被截断。

**`quality-review`** —— 成稿一致性审查，一份标书一次（自动修订最多四轮）。
要在整份标书里找矛盾、找评分点缺口、找编造的承诺和资质，**这件事没有推理做不了**，
是六个里唯一开 thinking 的。温度 0.0：审查结论不该每次跑出来都不一样。

## 上下文要求的来历

产品侧对每一次调用的输入都做了**有界召回**，不是把整份标书塞进去。下面是代码里的
硬边界：

| 环节 | 成分 | 字符上限 |
| --- | --- | --- |
| 正文续写 | 项目概要（按关键词召回） | 2,500 |
| | 技术评分要求 | 3,500 |
| | 选定范文分块（最多 4 块） | 8,000 |
| | 上一单元摘要 | 1,600 |
| | 全文承诺口径 | 2,400 |
| | 上文正文 + 章节开头 | 2,800 + 1,200 |
| | **合计** | **≈ 22,000** |
| 目录骨架 | 参考素材 | 50,000 |
| 项目概述抽取 | 选中的源正文 | 48,000 |
| **一致性审查** | **每章正文摘录 × 章节数** | **16,000 / 章** |

**审查这一档和其余五档不是一个量级。** 前五个的输入有界且恒定——标书再大，
一次送进去的都是那几万字符。审查不是：它把所有章节一起送，所以上下文需求随标书
规模线性增长。按每页 700–1100 字符估，100 页约 7–11 万字符，500 页约 35–55 万字符；
中文按 1 字符 ≈ 1 token 保守估算，**500 页那一档需要 25 万 token 以上的上下文**。
选型时这是硬约束，超了不是降级而是直接失败。

## 模型能力要求（四条硬性，与档位无关）

1. **结构化输出** —— AI 响应一律经 Pydantic 校验，自由文本不直接进业务库。
   结构化输出失败映射为 502 并触发一次修复调用；模型这项能力不稳，成本直接翻倍。
2. **中文长文写作** —— 不是「能说中文」，是能在中文里保持专业密度与术语一致。
3. **长上下文** —— 见上。审查档 ≥128K，其余 ≥32K。
4. **thinking 可开关** —— 六个里五个要关、一个要开。不能关的模型会让那五个 endpoint
   的补全预算被推理吃掉；不能开的模型做不了审查。

参考实测：本产品直连时代用的是 `deepseek-v4-flash`（fast）与 `deepseek-v4-pro`
（quality）。具体挂哪个模型归运营决定，这里只给能力要求——
**「quality + 长上下文 + thinking」三个条件同时满足的那一档，是本次扩模型最该
优先解决的**。

## 请 Atlas 线做三件事

1. **登记六个 endpoint**，按上表配置。
2. **给产品 `tenderforge` 授权**（`product_endpoint_grants`）。这是产品轴授权，
   **不需要租户**——也正因如此，它容易被当成「还要等租户开通」而推迟。
3. **确认各自的 `fallback_model_code` 故障转移链**。产品侧收不到「运营重指了模型」
   的任何信号，只能从非流式响应回显的 `modelCode` 观测。

## 授权到位之前，产品不会停

产品侧留了降级开关 `ATLAS_USE_DEDICATED_ENDPOINTS=false`，此时全部落到
`chat/default`。「Atlas 通了但专属 endpoint 还没授权」那段时间一定存在，而在它期间
让每次调用都 403 等于把产品停掉。

**代价要说清楚**：所有 operation 共用一套生成参数，也就是失去按任务分档本身——
审查没有 thinking、正文温度不对、骨架可能被 `max_tokens` 截断。这是能跑，不是能用。

## 怎么确认配对了

- `GET /v1/endpoints` 应返回这六个，`state` 全为 `active`。出现 `missing` 说明
  授权指向了一个不存在的 code。
- 逐个发一次最小调用，确认不是 `403 NOT_ENTITLED` 也不是 `404 ENDPOINT_NOT_ROUTABLE`。
- 审查那一档单独验一次**长输入**——它是唯一可能撞上下文上限的，而撞上时的错误
  来自上游，读起来不像「上下文不够」。

## 产品侧已就位的部分（供对账，不需要 Atlas 做什么）

| 契约要求 | 产品侧实现 |
| --- | --- |
| 产品集成用 `endpointCode` | operation → endpointCode 的唯一映射点，不散在调用处 |
| `taskId` 必填、跨产品同值 | 由 Java 入站带入并透传；缺了直接失败，不兜底生成新 id |
| `tenantId` 必须是平台租户 UUID | 取自票里的 claim，不是产品码 |
| 错误信封照读 `retryable` | 不按状态码自行归类 |
| 不在产品仓发明被调方的接口形状 | 生成参数不塞请求体，改为本函 |
